# 服装设计 Agent 框架

本系统的目标是把设计目标、素材、执行、候选与人工决策连成可回溯的设计路径。
当前主框架对应论文图 8：`Information Integration → 单个 Planner → Action Enablement`
组成协作循环，执行回执成为下一轮观察。Agent 产出建议，设计师决定采用、否决、
应用修订以及何时生成。Planner 协议为 `workflow-planner/2`，服装领域简报与评价继续
使用 `fashion-agents/1`。项目主入口使用持久化节点图；原有串行 `AgentRun` 保留历史与执行。

## 图 8 的实现与状态边界

`InformationIntegrationService` 投影初始目标、当前步骤目标、设计轨迹、对话、隐含意图
和工具信息六类上下文。不可变节点版本、真实执行、人工决定与原文是事实依据，摘要
不能覆盖它们。对话压缩保存目标变化、被纠正理解、决定与未解决问题，未读部分保持
覆盖标记；需要细节时可以补读项目内原文。

历史主窗口最多选择 200 个版本，依次优先焦点当前版本、最新图修订、焦点相关分支和
近期记录，并补读选中版本的边界前驱。版本轨迹、语义差异和修改记录正文分别限制为
48,000、24,000 和 16,000 字符；超大版本可保留 `detailsIncluded=false` 的元数据。
覆盖信息区分历史确实缺失、未加载、未投影和只读元数据，`absenceClaimAllowed=false`
禁止把空的尝试、执行或决定解释为从未发生；资产决定是带时间的事件，不是版本创建时的状态。

`WorkflowCoordinator` 调用单个 Planner，内部支持 `reply / clarify / read / propose`。
`read` 只能补读项目内节点、尝试、分支历史、对话和实际图片，不执行设计工具；每回合
最多三轮补读、一次校验修复、五次 Planner 调用。计划保存当前目标、阶段、证据和完成
条件，可以随新结果修订，不预先提交整条可执行工具链。

分支补读按创建时间与 ID 的稳定游标分页，大记录以字段路径和字符范围分片；同一次
协调运行中重复相同分支请求继续未读部分，项目、分支或图修订不同则隔离进度。
版本补读保留图修订、时间、前驱、修改来源和修改编号；长对话原文也按消息分段续读。
单次补读正文最多 8,000 字符，一次协调运行累计最多 24,000 字符，未读范围明确返回。
这些机制提供可追溯的有界读取，不表示每轮全量加载或支持完整过程重放。

统一工具库位于 `packages/shared`，目录同时提供工具标签、输入槽位、参数 schema、
输出和限制。当前四类工具全量提供，不使用 embedding 或频率排序。数量、负向提示、
尺寸、质量和参考配置由同一契约校验；参考角色与权重是提示词引导，不能当作模型
保证的精确物理控制。版本恢复继续通过真实历史入口完成。

动作使能只接受创建工具、配置未执行工具、从已执行工具派生分支三类业务动作。提案
预览同时展示参数、输入替换、保留项与影响范围。未执行工具确认后原卡更新；执行过
的工具不能覆盖。模型没有任意数据库或图修改权限，接受建议不创建生成任务。

`WorkflowNodeVersion` 的 UUID 和递增版本号记录语义状态，输入绑定引用来源节点版本；
当前画布仍使用稳定 `nodeId`。图修改、前后快照、版本与语义事件在同一事务保存。
状态切换和布局拖动不产生新的设计版本。已有图首次需要版本时只建立当前基线，不
补造过去修改。`WorkflowExecution` 汇总一次主动执行的全部尝试，`WorkflowAttempt`
保留每个候选的冻结输入、节点版本与生成任务。

候选设计路径从实际结果的不可变版本出发，沿版本输入绑定读取冻结来源，并按精确
生产尝试或生成任务归属关联输出，不能用当前卡片或最新重试替代旧事实。旧路径回退
真实资产血缘；缺失、冲突或达到读取预算时保留不完整标记。
生成结果同步将结果节点、尝试终态与执行终态回执同事务提交；恢复结果回填将工具／
结果节点、不可变绑定、执行记录与终态回执同事务保存。幂等重放不重复创建历史。

生成成功、最终失败、取消与审核失败和 `WorkflowOutbox` 回执同事务提交；回执只含
内部标识、终态和结果资产编号，不携带图片字节。API 后台消费者租约领取、幂等回填，
定期恢复扫描覆盖重启、队列唤醒丢失和任务先完成后关联的情况。数据库是投递依据，
Redis 用于唤醒，SSE 用于即时通知。多个候选合并为一次执行观察，模型分析失败不
回滚已落库资产或执行事实；后台建议仍需人工确认。

`AgentTurn` 保存用户或执行观察回合的租约、快照与预算；`AgentPlanRevision` 保存计划
修订。用户消息、纠正与项目开关递增会话 `intentEpoch`。后台提交校验意图、上下文、
摘要、图和计划版本；接受提案再次校验节点版本、执行状态和计划意图版本。旧响应
不能覆盖更新后的人工决定，已接受请求按原编号幂等重放。

新接口与兼容入口：

- `GET /projects/:projectId/workflow/tools` 返回完整工具目录与启用版本。
- `GET /agent-conversations/:id/plan` 读取当前协作计划。
- 工作流消息可关联被调整的提案，拒绝提案可附理由；无理由的跳过不是偏好证据。
- 节点执行可传 `conversationId`，执行观察只回到发起会话；旧客户端缺少归属时仅记录项目事实。
- `POST /projects/:projectId/workflow/agent-settings` 接收 `{ "version": 1 | 2 }`；`1` 暂停新版规划和后台建议，保留手动画布、资产、回执及历史读取。
- 旧 `POST /agent-conversations/:id/plans` 仅重放已存在请求，新请求返回 `410 LEGACY_AGENT_PLAN_RETIRED`；旧运行执行和读取接口保留。

上线顺序为应用迁移 `20261016090000_fig8_workflow_collaboration`、生成并构建内部包、
重启 API/Web/Worker，再验证工具目录、执行回执与助手计划。项目默认启用版本 `2`。
回退使用项目开关并保留新表和历史数据；不会恢复旧关键词或六步计划的新建路径。
恢复版本 `2` 后继续从当前事实规划，暂停前的待审新版提案已失效。

## 持续设计协作与全图上下文

主助手使用 `workflow` 会话和持久化消息，统一回答、澄清与下一步建议。Planner 直接
读取 `DesignContext`，根据上下文返回 `reply / clarify / propose`，不再由关键词预先
决定主助手使用哪个工具。旧会话保持 `legacy`，历史记录可查，不补造缺失来源。

`DesignContextService` 从权威图投影全部节点目录、带端口的边、自然语言分支轨迹、
真实执行尝试、冻结输入与提示词、候选评价和人工决定。焦点分支的历史优先读取；
未连接素材也进入全图目录。详情、原文和图片有明确预算与覆盖记录，缺失历史、未读
图片和省略内容均不能当作不存在。资料文字、图中文字与模型摘要都仅作为材料数据。

项目初始目标、当前目标、要求和偏好跨会话共享，并保存来源及修订。会话任务、明确
焦点和对话摘要单独管理；点击查看节点不会悄悄切换讨论焦点。目标更正保留旧版本，
不回写已执行工具。画布中的约束按实际分支投影，解释性条件始终为推断偏好，非视觉
条件保留测量或规格资料要求。原始对话完整保存，长期摘要使用带消息来源的原文提要，
摘要游标只推进实际处理的消息。
先打开空画布、再添加唯一需求时也会保存初始目标；后续添加分支不会覆盖它。

图片视觉摘要独立于素材用途标签。上传、生成与趋势封面就绪时通过 BullMQ 分析，历史
图片在读取上下文时补齐。缓存绑定图片内容、模型和摘要版本，保存主体、廓形、可见
结构、颜色、表面纹理与无法确定项。助手同时获得全图摘要索引及至多八张相关实图，
每张图明确绑定节点；公开上下文不返回私有存储地址或图片字节。首次补齐会调用现有
视觉模型，Worker 未启动或分析失败时保留真实未就绪状态。
视觉契约 `visual/2` 禁止推测纤维成分；失败缓存冷却后通过原子领取恢复任务，避免永久失效或并发重复调用。

`HiddenIntentMiner` 独立于 Planner，从至少两次同一因果分支中真实人工确认的输入或
参数差异挖掘偏好，逐条核对版本和原文证据；布局、系统填充、技术失败、取消和审核
失败不属于审美证据。推断保留作用范围，不能升级为必须要求。停用记录参与后续规划，
不能由摘要或旧推断自动恢复。
项目上下文更正使旧提案失效；布局拖动不改变语义版本。
上下文栏展示完整偏好目录及停用记录，新会话未设焦点时也能查看和纠正分支偏好；
Planner 仅使用当前范围适用的有效项。

信息整合、Planner 和动作准备职责分离。动作模块只编译经过校验的业务动作和输入连线，
不接受模型提供的任意图操作。修改必须保留母图分支约束，评估不能替换明确引用的候选，
跨分支约束选择需要明确来源。模型输出或输入非法时最多修正一次，再返回澄清。
主需求分析只调用独立 `curateBrief()`，不再额外生成旧六步计划；评价使用候选生产尝试
中的真实冻结提示词。版本恢复仍由真实历史选择入口完成。
主评价同时读取统一上下文中该候选祖先的尝试、人工决定和有效分支偏好，作为辅助背景
冻结到评价尝试中；提案的具体检查重点单独传递，不能覆盖候选生成提示词，也不能将
当前项目新目标或其他分支偏好加入既有约束的符合性检查。

每会话的活动回合采用租约，消息编号校验内容和引用。最终提交同时校验会话焦点版本、
项目上下文版本和图语义版本；记忆修订、提案及助手消息在同一事务保存。过期响应不能
覆盖新任务。提案接受与图提交、接受／拒绝状态转换也采用原子校验。认知范围与执行
输入分离：接受建议只加入画布，付费图片操作仍需用户主动执行工具。

主要接口：

- `POST /projects/:projectId/agent-conversations` 支持 `mode: "workflow"`。
- `POST /agent-conversations/:id/workflow-messages` 接收文字、引用、焦点和幂等编号。
- `GET /agent-conversations/:id/messages` 恢复消息及提案的最新状态。
- `GET/PATCH /agent-conversations/:id/context` 查看和纠正目标、焦点及偏好。
- `GET/PATCH /projects/:projectId/design-context` 管理有来源、有版本的项目记忆。

新增数据包括项目上下文及修订、会话摘要、视觉摘要缓存，消息与图提案建立显式关联。
真实验收脚本 `scripts/verify-workflow-assistant.ts` 使用隔离项目、真实模型、PostgreSQL、
BullMQ 和私有存储，检查全图回答、参数配置、执行观察和跨会话继承，不生成新图片，
结束后清理测试记录。兼容入口已经进入新 Coordinator，不能充当重构前基线。

`scripts/evaluate-workflow-fig8.ts` 提供十个固定服装上下文场景、轨迹／对话／隐含意图
八种组合及三次重复，共 240 个实验条件。默认只生成清单和空白盲评表，不调用模型。
真实运行需提供渠道单价与调用、费用上限；原始用量、耗时、错误和未知费用均保留。
四维专业评分由盲评者填写；重构前固定结果可以导入配对，缺少基线或评分时不报告改善。

## 主工作流运行时

主画布的权威数据是项目级 `WorkflowGraph`，不是 tldraw 快照。资产包含需求、参考、
约束、候选与评价报告；工具包含需求分析、方案生成、评价、修改与版本恢复。每条边有
输入槽位，服务端校验类型、归属、无环关系和输入就绪状态。位置修订与语义修订独立，
拖动节点不会使建议失效。已执行节点及其输入被冻结，修改产生新分支。

| 环节       | 主工作流中的实现                                                                         |
| ---------- | ---------------------------------------------------------------------------------------- |
| 上下文     | 全图目录与分支、真实历史、完整持久对话及有界摘要、项目记忆、视觉索引与明确引用           |
| 下一步建议 | Planner 决定回答、澄清或建议工具；合法提案保存为 `WorkflowProposal`，以虚线预览             |
| 人工确认   | 接受建议仅提交图变更；付费图片操作仍需主动执行节点                                       |
| 需求分析   | 复用领域简报与确定性约束审查，约束作为有生产者和来源的资产节点保存                       |
| 工具执行   | 每个工具使用实际输入节点生成冻结快照；`WorkflowAttempt` 绑定现有生成任务、模型参数与重试 |
| 图片评价   | 读取实际候选图与相关约束，逐候选输出报告；非视觉条件保持“无法判断”                       |
| 修改与决定 | 明确绑定母图，产生独立候选；人工选择及理由追加到原有资产决策，不删除其他候选             |
| 恢复与回填 | 幂等请求、任务和资产标识避免重复投影；版本恢复创建工具与结果，旧路径仍可查               |

新运行时不把多输入 DAG 压回旧的六步单来源序列。它只执行设计师触发且输入就绪的
工具节点，生成与编辑继续使用现有 Amux、编译器、额度、BullMQ 和私有存储。
旧白板只供查看或引用资料，普通绘图连接不参与新图执行；缺少证据的旧路径保持不完整。

新接口位于 `/projects/:projectId/workflow`，图、提案和尝试分别保存；旧接口与数据保留。
下面职责表中的六步规划、动作租约和 `AgentRun.contextSnapshot` 描述的是旧串行框架历史，
领域简报、约束校验和实际图片评价能力由主工作流继续复用。

| 设计规划 Agent   | 校验后的简报、工具契约、选中资产、对话上下文                 | 最多六个节点、每节点目的、绑定约束、验收观察项           | 一次结构化模型调用；只能选择注册工具与合法前序来源               |
| 约束审查器       | 来源证据、简报、节点及依据                                   | 引用检查、约束覆盖、未绑定项警告                         | 确定性校验；无额外模型调用；解释性约束不能提升为必须要求         |
| 工具执行器       | 人工确认后的节点、当前实际采用来源                           | 编译快照、执行尝试、生成任务及候选                       | 现有生成队列；只执行当前获准节点，保留重试历史                   |
| 候选评价 Agent   | 实际候选图、实际编辑母图、冻结执行提示词、设计简报           | 每个条件的符合、存在问题或无法判断，以及观察与下一步建议 | 人工发起的一次视觉模型调用；不自动采用或否决候选                 |
| 修订 Agent       | 具体尝试的失败或否决、相关评价、旧执行输入、当前已保存提示词 | 修改建议、修改理由、应保留部分、原值与建议值             | 人工发起的一次模型调用；应用建议单独校验版本，应用后仍需主动执行 |
| 证据管理与运行时 | 资产归属、决策作用域、版本号、动作租约、尝试快照             | 有界证据与可追溯状态                                     | 确定性服务；校验所有写入，不让模型拥有数据库或状态转换权限       |

这里的协作通过带类型的产物进行，不让多个模型无限互相讨论。当前共用已有模型客户端，
没有引入新的模型服务或 Agent 依赖。规则校验与权限检查独立于模型输出。

## 设计约束是核心协议

约束覆盖廓形、结构、材质、色彩、风格、功能和展示方式。每条约束包含：

- 设计要求，以及要求、保留、修改或避免的模式。
- 必须满足或偏好，以及用户明确要求或模型解释的来源类别。
- 证据编号和原文引用，能够回到当前目标、白板元素或相关设计决策。
- 验证方式：视觉观察、需要测量或需要规格资料。

明确要求的引用必须来自已提供的证据。单独来自旧决策的约束仍是有作用域的历史参考，
不能成为本轮必须要求。模型解释只作为偏好。未知项应保留，不能凭图片推断真实纤维
成分、尺寸、合体情况或可生产性。非视觉条件在候选评价中必须为“无法判断”。

节点的约束覆盖表示“规划了在哪一步处理该条件”，不表示生成结果已经符合。节点被
手动修改后，不继续展示已失效的模型依据；需要重新检查绑定与覆盖。

例如用户要求“保持立领和藏蓝色，把袖子收窄”，系统应分别记录保留立领、保留色彩、
修改袖宽。用户否决“袖子仍然太宽”后，修订应集中处理袖宽，不能自行更换衣领或面料。
这个否决也不能自动变成其他项目的“喜欢窄袖”偏好。

## 可回溯的闭环

```mermaid
flowchart LR
  A[目标与选中证据] --> B[整理设计简报]
  B --> C[规划节点与验收项]
  C --> D[确定性审查]
  D --> E[人工编辑与执行]
  E --> F[冻结尝试与真实候选]
  F --> G[人工发起领域检查]
  G --> H[逐条件观察报告]
  F --> I[人工采用或否决]
  H --> I
  I --> J[根据具体反馈提出修订]
  J --> K[预览与应用建议]
  K --> E
```

运行、简报、依据、报告与建议持久化在原有 `AgentRun.contextSnapshot` 中；执行尝试保留
独立输入和编译快照。领域报告不写入 Worker 管理的生成任务输出，避免相互覆盖。
所有图片操作仍经现有编译器与生成队列，来源只允许本次选中设计或前序实际采用结果。
节点依赖支持分支，但运行仍按顺序逐步执行；没有自动执行整个图或并行生成。

动作接口为 `POST /agent-runs/:id/agent-actions`，支持 `evaluate_candidate` 和
`refine_step`。应用接口为 `POST /agent-runs/:id/agent-actions/:actionId/apply`。
两者均使用运行版本号。评价绑定具体候选与尝试；修订绑定具体失败或否决的尝试，
并以当前已保存的可编辑提示词为修改基准，避免倒退用户已经完成的修改。

同一个动作请求编号重放原结果，网络不确定时可以安全重试；已失败动作的主动重试使用
新请求编号。模型调用在数据库事务之外进行。短事务领取动作和提交结果，只有有效租约
及匹配版本可以回写。人工决策或修改使正在分析的动作失效；迟到响应不能覆盖人工操作。
超时动作在读取时标记失败，读取本身不会再次调用模型。每运行最多保留 48 个动作，
超过上限拒绝新请求，不删除历史以重新开放请求编号。

应用修订再次检查节点、最新尝试和原提示词；过期建议不能覆盖新值。应用只是保存节点
输入，不创建生成任务，也不修改旧尝试。API 只返回领域产物白名单，不公开模型输入
图片数据、签名 URL、请求编号、租约或内部快照。

网络、队列或额度等执行失败不是服装缺陷。对此修订流程确定性保留当前提示词，解释
应处理执行问题或重试，不调用模型虚构设计改动；只有具体设计否决进入模型修订。

## 技术壁垒如何积累

可积累的资产不是 Agent 数量，而是领域约束协议、带证据的设计路径、具体图像与专业
评价、失败原因和有效修订之间的对应关系。当前实现提供这些资产的可记录、可审计
基础，还没有自动训练模型或证明比通用助手更准确。

验证应把可自动检查的行为与专业判断分开：

| 场景                         | 自动回归检查                             | 专业评价目标                 |
| ---------------------------- | ---------------------------------------- | ---------------------------- |
| 保留衣领与色彩，只收窄袖子   | 引用合法、保留条件仍在、修订绑定正确尝试 | 是否真的只改变目标部位       |
| 换材质但保留轮廓             | 条件覆盖与输入来源                       | 材质表现与廓形保持程度       |
| 指定 HEX 色卡                | 原始色值和证据可回溯                     | 与目标色卡的视觉接近程度     |
| 从图片判断纤维成分或精确尺寸 | 非视觉条件强制无法判断                   | 不确定性表达是否合理         |
| 相互冲突的设计目标           | 保留未知项和未绑定警告                   | 是否识别冲突并提出可用取舍   |
| 否决某张图的袖口             | 反馈仅绑定该图与尝试，不成为全局偏好     | 下一轮是否修复缺陷并保留优点 |
| 外项目资产、取消与同时修改   | 归属、版本、租约、幂等性校验             | 不适用，必须由服务端保证     |

专业评测应收集经授权的任务、图像、专家逐条件标注和最终人工选择，按项目划分训练
与保留测试集，避免同一设计路径泄漏到两边。以相同模型、图片和调用预算比较原有
单次规划、领域简报、增加评价、增加反馈修订等方案。记录来源准确率、条件遗漏率、
评价与专家的一致性、错误自信率、保留条件破坏率、达到采用所需尝试数、时间和成本。
只有独立测试上的改善才能支撑技术优势。

后续可接入经过验证的面料知识、系列 DNA 与领域检索，以及设计师授权的项目偏好。
这些能力应拥有来源、权限、版本和评测，不应从零散点赞或否决自动推断稳定偏好。
生产规格、打版、合体和成本判断需要相应工具与数据，当前不能由视觉模型代替。
