# 透明材质实测与定位记录

2026-10-30，进行中。此记录说明已观察到的失败及排查证据，不代表透明材料验收通过。完整矩阵见 [PROVIDER-REALISM.md](PROVIDER-REALISM.md)。

## 已证实的现象

- 原设计为茶色半透明镜片及象牙色无衬蕾丝袖。真实转换返回了有透明背景的 PNG，但镜片／袖部几乎不透出底色；背景透明不等于材料透明。
- 眼镜第一版的两个镜片内部采样 alpha 都为 253/255。加强局部透射约束后的 Sunburst 第二版为 252/255 与 253/255，白、场景灰、深灰三底可见的问题仍然存在。各次原图、采样及拒绝记录独立保留。
- 第二版眼镜 `candidate-provider-0.png` 与最终入库下载的 `candidate.png` 编码字节、SHA256 和解码 RGBA 均一致，大小 995411 字节。蕾丝亦为原始与入库字节完全一致。证据为各案 `alpha-chain-audit.json`。没有发现 worker 重编码或去底处理压掉材料透明度。
- 实际 multipart 请求包含 `background=transparent`，输出为四通道 PNG；因此不能用“忘了请求透明背景”解释此次失败。
- 对同一眼镜设计与目标区域进行一次 Flare 对照，来源、实际提示、尺寸、质量及透明参数保持一致，只改变模型。三底人工复核仍未通过，独立记录于 `attempts/transparency-flare/`。一次受控失败不等同于证明该模型永远无法处理透明材料。

## 已落入产品的改动

1. 所有单品提取、补全和侧图转换共享条件式透明材料约束：仅已知镜片／网纱／蕾丝区域保留局部透射，实体内衬、缝线、框架保持不透明；不允许全图统一降 alpha 或把镜片挖成空洞。
2. 正面、侧挂候选及挂架预览共用白／场景灰／深灰底色切换，只改变预览背景。核对真实被拒绝候选能直接看到镜片不透和蕾丝烘白，操作不会创建任务。
3. 不合格候选不执行确认，不改原始供应商 PNG，不把透明背景检查或内容审核当成材质审核。

## 后续实验边界

已以第二版眼镜候选的真实资产为输入，使用现有 `isolated + extract` 路径进行一次局部透明修正，未重新上传设计根，实际 worker 的父资产及根资产均校验一致。新镜片内部 alpha 样点为 197/255 与 214/255，其他内部点 191/255；实体框及铰链仍为 252–253/255，并非全图统一降透明度。相对于先前近不透明镜片已有改善。

初次独立复核指出大面积棕灰反光可能呈现雾面感，随后使用白／深底细节和高对比竖纹背景检查：条纹边界可连续透过两个镜片，框体仍为实体。这一版正面经两人复核后确认，保留反光较宽及茶色较深的限制，不宣称光学仿真。`lens-striped-background.png` 只把原 PNG 合成到分析背景，原始供应商图片未修改。逐图审核结论以同 hash 的正式 review 为准。

该正面生成轻侧图后，镜片再度变成 alpha 253/255 的近不透明填充。`side-support-v2/accessory-translucent-glasses/side-review.json` 已独立拒绝，正面通过不传递给侧面。针对这种退化，生产准备契约增加显式的侧候选修正来源：必须是相同项目、单品修订和方向下已完成的候选，只进行 `isolated + extract`，不附加姿态参考、不重新转向；新任务、父资产和原始侧挂绑定均保留，仍需重新核对后采用。

该侧候选经上述真实修正后，在 `side-alpha-repair-v1` 得到局部透射结果：镜片样点 alpha 201/207，实体框为 251、铆钉为 253。三底与条纹复核通过后实际确认；新侧图仍保留茶色和较宽反光，不把两次失败记录改为成功。前后图保持独立审核，页面托架验证也使用本次新 hash。

蕾丝同样走独立候选修正后，12000 个袖部采样像素中 11999 个 alpha ≥245，条纹不能透过网眼，仍未通过。一次切换至 `openai/gpt-image-1.5` 的真实对照请求返回 HTTP 403，无结果资产；不能据此评价其材质能力，也未自动重试。1.5 的 `input_fidelity` 默认值与 2.x 不同，记录中保留这一差别。

随后使用现有生产 `inpaint` 链路和两袖独立蒙版：蒙版与来源同尺寸，透明区域允许修改，衣身、领口及袖口受保护；原图未本地修饰，蒙版作为私有资产记录到设计步骤。真实 multipart 带蒙版，但供应商输出 RGB，外部和袖网眼均画出了棋盘图案，不能当透明素材。对此结果再做一次真实提取，外部背景得到 alpha，袖网眼仍主要不透明（同 12000 像素 ROI 中 11602 个 alpha ≥245），条纹复核失败。两阶段的任务、原始结果和拒绝分别保留在 `lace-inpaint-v1`、`lace-inpaint-extract-v1`；没有将像素处理后的图冒充模型直接输出。

任何新处理方式仍必须保存原图、原拒绝、输入参数、供应商输出、候选及逐图判断；不能手工改测试图片后冒充供应商直接输出。

## 细网保留诊断（尚未验收）

`lace-green-probe-v1` 使用同一来源和袖部蒙版，实际调用局部编辑生成绿色孔隙中间图。该图明确标记 `processingProbe`，不能直接确认入架。纯算法诊断仅在蒙版允许的范围估计 alpha，保留原图全部 RGB 和受保护的衣身、领口、袖口，输入与派生图 SHA 分别记录。白／灰／深底比较中，花瓣和内衬得以保留，背景也能穿过袖面，但部分原有细网被去掉，出现过大的空洞；因此目前仍不通过。

补充的原图高频细节诊断能恢复部分网眼内细点，尚不能证明连续网线完整，未进入产品算法。可复现脚本为 `scripts/manual/diagnose-wardrobe-material-alpha.mjs`，只写入忽略的 `output/` 并将输出标为 `algorithm-derived-diagnostic-not-provider-raw`、`approved: false`。它不会覆盖原始供应商输出、创建项目资产或确认版本。

随后真实执行 `lace-green-net-v2`：第一图保留完整原候选，第二图使用同一原图左袖 `(150,600,100,260)` 的原像素 ROI，蒙版不变。局部编辑的多参考扩展由服务端验证所有参考和蒙版属于当前项目，第一图必须是父资产，私有下载签名及设计步骤来源保持顺序。裁切的放大图只供诊断，实际 API 使用未放大的 ROI。

这一版原始中间图仍不可直接入架：它没有成品 alpha，且模型在保护区域外增加了渐变和文字。固定 gain 0 的派生候选不采用这些 RGB；全部 RGB、蒙版外 RGBA 均来自原图，仅在明确选择区域估计 alpha。独立复核确认两袖连续细网、花瓣对齐和条纹透射成立，衣身内衬保持不透明，批准其进入生产候选流程。原始图与派生图分开审核；尚不能由此批准侧挂图或任意绿色、深色透明织物。

算法已经作为 `packages/ai/src/material-alpha.ts` 固定版本 `green-dominance-original-rgb-v1` 实现：只有处理图的 G 大于 R、B 时，以 `max(R,B)/G` 估计透射 alpha，与原 alpha 及蒙版权重组合。没有高频补偿、模糊、全图降透明度或色彩调整。18 项单测通过；使用三份真实输入在内存计算的全部 RGBA 与被独审候选逐字节一致，记录于该案例 `material-alpha-module-equivalence.json`。

生产接口将源图、真实成功 INPAINT 中间资产和对应蒙版重新验证后保存为新的私有派生资产。来源设计步骤记录三资产、四份 SHA、算法版本和处理统计；返回新的待核对准备记录，不能自动确认。新中间图有独立标记，不能直接以已有素材入架。浅色蕾丝／网纱的选择区域、原像素细节参考、三底核对和显式生成仍是必要步骤；检测到所选源区域含绿色织物时拒绝这一特定处理方式，不能假设键色与真实绿色材质可区分。

本轮查阅的 [Amux 图像参数文档](https://amux.ai/api-reference/models/create-image) 及 [Flare 编辑接口](https://amux.ai/api-reference/images/gpt-image-2-5-flare-edit) 确认两种模型使用兼容的图片编辑接口、透明背景和 PNG 参数；这些接口说明没有保证任意半透明材料的逐像素正确性。实际结果仍以本轮原始 PNG 与三底复核为准。

## 侧挂图的遮挡关系

透明材质不等于整块袖子都应该透出背景。侧挂时，近侧薄纱袖的上段可能覆盖在实体衣身或内衬前方；这里应保留后方衣片，只有下摆以外真正露空的袖网才应该透出场景。`lace-chest-native-v1` 的胸腹结构已经修正，但下段露空 ROI `(495,1120,100,250)` 仍为近不透明 alpha 253–254，需要独立处理。

初拟的全袖修复蒙版会误伤上段袖后衣身，已在收费调用前撤回并归档于 `lace-side-green-net-v1/superseded-full-sleeve-mask/`。后续改为只选择明确露空的袖段；不能用全袖均匀透射作为通过标准。生产修复提示和涂选界面也已补充这一遮挡规则。通过派生和三底复核前，新侧图保持未验收。
