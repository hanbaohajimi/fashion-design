## 实际契约与覆盖范围

已核对现行源码，而非从普通服装名称推测：

- `packages/shared/src/wardrobe.ts` 支持 10 类：top、outerwear、bottom、onepiece、shoes、bag、hat、scarf、belt、accessory；支持 hanger、clips、hook、shelf 四种独立展示挂具。
- `apps/web/src/modules/board/generation/collection-types.ts` 与 `apps/api/src/modules/collections/collections.schemas.ts` 一致，包含 jacket、coat、vest、shirt、blouse、tshirt、top、knit、pants、shorts、skirt、dress、jumpsuit 共 13 个常规设计输入，以及 custom。
- `packages/shared/src/studio.ts` 的款式 category 是自由文本；品牌面料偏好、系列 fabrics 也开放。因此任何有限矩阵都不能宣称“所有设计均可靠”。本矩阵覆盖所有已有类别和输入码，再用困难材料／结构扩大代表性。
- vest 本例是西装背心，映射 top；coat/jacket 映射 outerwear；pants/shorts/skirt 映射 bottom；dress/jumpsuit 映射 onepiece。custom 必须按实际形态明确映射，不能全部落入 top。
- 主链为 `sourcePrompt` 真实生成测试设计草图，再经真实 `Wardrobe.prepare(sourceKind=sketch, mode=complete)` 转换。生成测试设计是测试输入，不声称来自真实用户的已批准款式；明确文字规格仍是验收依据。
- isolated、worn、outfit 源类型以及 extract 保留草图表达的路径不由该主链自动覆盖；若对外声明这些路径也合格，必须另补相应源图及对照。不得因为 extract 保持线稿而套用 complete 的写实标准。

执行资源：[wardrobe-provider-cases.json](../../../scripts/manual/wardrobe-provider-cases.json)。29 个独立案例覆盖 10 类、14 个输入码、4 种挂具。每项包含 sourcePrompt、notes、expectedMaterial、expectedShape、support、reviewChecks；禁止为凑覆盖重复同图或改标签伪装另一品类。

## 每一案的实际执行顺序

1. **先审设计源。** 按 JSON 明确规格逐项查颜色、版型、闭合方式、数量、长度和材料表达。源图错了即 source rejected；不得把错误源图当真值后宣布转换保真。草图未画出的材质由明确 notes 补充，不能由模型私自选择。没有给定的背面／内部结构记为未知。
2. **真实转换留证。** 保存原 source、实际生产输入和供应商原始输出、任务与入库候选。真实 HTTP 成功、审核成功、任务成功、有效 alpha 是链路证据，不是视觉合格。直接文生图最终照片不能充当草图转换验收。
3. **逐图审核正面。** 对比规格、草图及候选，先审整件再看领口／腰头、袖口／裤脚、面料／印花、细件四组局部；白、场景灰、深灰三底核查 alpha。准确记录候选 hash，只有人工判断通过的该 hash 可以用于隔离验证项目 confirm。
4. **审核独立侧挂视图。** 若产品提供独立侧图，要用已审正面作为依据经实际链路生成并保存单独的 task/asset/hash。检查共享细节和重力；单纯 CSS 压窄正面只能记为 projection fallback，不能写成独立侧挂纹理通过。无真实侧背资料时必须标明是生成陈列视图，不能声称还原未知背面。
5. **渲染验证。** 使用实际候选 bytes、原 category/display、确认的 anchor/bounds/supportWidthRatio 和真实侧图。先静置、悬停转正、反向切换、聚焦、关闭，再测手机；实际显示挂具仍由应用绘制，候选不得烘焙挂具。挂点坐标相对完整原图，不能混用 alpha 裁切坐标。
6. **保留所有尝试。** 失败／重试／修正源图不能删掉。最终通过与首轮通过分别记录；只换提示成功的结果叫“迭代后通过”，不能掩盖首次错误或将缺图计为通过。

## 逐维判据与直接失败条件

每维只能记 pass、fail、pending；不以平均分抵消错误。只有该阶段所有必需维度通过，阶段才通过。无法根据资料核对的点记 pending，附缺失依据。

| 维度 | 必须看到 | 直接失败例子 |
| --- | --- | --- |
| 源规格一致 | 源图符合文字规格；数量、颜色、基本廓形、部件闭合一致 | 要求无帽却多帽、六扣变五扣、白底蓝花变另一图案；源错误后仍作真值 |
| 正面保真 | 领、袖、门襟、口袋、腰线、下摆与鞋包配件对应，允许由平面草图变自然悬挂的有依据形态变化 | 丢肩带、裤腿粘成裙、左右鞋复制同一只、擅加背面装饰、把文字/印花改成乱码 |
| 材质 | 织纹／毛向、厚度、缝线和有材料依据的反光；亮片为离散小反射，缎面有连续转折，绗缝保留填充 | 针织变印刷条纹、羽绒被压平、羊毛变塑料、亮片变整面金属、皮革变无纹理平色 |
| 重力与承重 | 材料从真实支撑区域向下，柔软件有连续折弯，硬挺件保留设计结构 | 袖子向上漂浮、衣身由隐形人体胸腹撑住、下摆无故水平伸出、长带中途悬空断裂 |
| alpha 与完整性 | 整件完整，透明孔/网眼和半透明材料区分，细毛/流苏根部连续，三底无背景残留 | 假棋盘格、白方块、整圈白晕、残留人台/道具、细镜腿被抠除、蕾丝网眼填死、衣摆/鞋底被裁 |
| 独立侧图一致 | 颜色/材质、领口、袖型、长度和可见图案部分对应正面；自然折叠形成窄侧形 | 把正面印花完整复制到背面、反转文字、换款/换袖、侧图靠裁切或拉伸假装窄、背面未知细节被写成事实 |
| 实际渲染 | 挂具与衣物接触正确，原图等比、不调色不裁切；正侧切换基准稳定 | 木架穿袖/帽、裤夹夹空白/裆部、包钩穿包身、鞋底浮托、镜框折断、侧图换向后接触点跳开 |

肩部衣架：钩、架颈与实际领后支撑轴对齐；肩部藏于衣物，不为某些款强行新增肩带。裤裙夹：左右夹真实腰头／礼服上沿；单一中心 anchor 并不能证明两夹都正确。挂钩：只能承托原有提手、带、扣框或明确折弯；不能穿透布面。置物托：鞋底、帽边、镜框／镜腿与托面接触，不能让整件悬空。当前四种挂具不能支持的结构应判该案未通过，不能靠错误挂点伪装支持。

## 尺度与近邻侧挂验证

第二段视频已直接复看默认和深绿卫衣悬停原帧。原网页约796×443px，杆约586px长；10件挂点间距约53px。正面短T约150px宽，侧挂约正面宽的25–32%，衣物有真实轮廓和局部厚度；它只是当前短上衣参考，不是所有品类统一物理尺寸。

- 对照场景把杆长固定在约590px后比较，避免拿整个录屏宽度缩放。上衣190px主体高度是既有短上衣渲染上限，不得套给长大衣、长裙、长靴或腰带。
- 接触检查以590px杆长场景为基准：接触点目视间隙应在约0–2px内，领后/挂具轴横向误差通常不超过2–3px；不对无对称结构强套中心线。目标是接触可信，数值不是服装物理标准。
- 正面／侧挂每件主体完整、等比。独立侧图接触点保持固定，不能通过非等比拉伸、镜像或伪背面追求占位宽度。
- 标签跟随实际 alpha 下沿，参考间隔约32–40px；不遮脚口、流苏或长带，手机不能让邻件溢出页面或堵住当前主体。等待动画结束后取稳定截图，同时保留连续反向操作录屏，防止只验收静帧。
- 至少记录三个混排组：A为深浅上衣/粗针织/绒毛/皮革，B为长外套/长裤/百褶裙/长裙/连体裤/无肩带礼服，C为鞋/包/帽/围巾/腰带/眼镜。各组保留真实品类和挂具；少于10个真实独立项时展示实际数量，不重复补齐。
- 每件都要在左右至少各一邻件的条件下检查（首尾项要检查页面边缘），手机至少测试390px宽；高于普通上衣的物件核对底部空间。10类覆盖与29款覆盖分别统计。

## 证据与审核文件

每案建议目录 `output/wardrobe-provider/<case-id>/`，保留 source-provider-*、candidate-provider-*、实际 candidate、source/candidate-call、HTTP/审核、任务前后状态、正侧资产来源和 hash；渲染截图另存浏览器输出目录。alpha 包围盒、尺寸和挂点写入 manifest，并与确认后修订中的权威元数据比对。

`review.json` 仅用于明确阶段审核，例如：

```json
{
  "decision": "approved",
  "stage": "front",
  "caseId": "top-green-sweatshirt",
  "reviewedBy": "independent-reviewer",
  "reviewedAt": "ISO timestamp",
  "sha256": "exact candidate bytes",
  "anchor": { "x": 0.5, "y": 0.17 },
  "supportWidthRatio": 0.62,
  "reviewChecks": ["逐项实际观察，不能批量填approved"],
  "sideApproved": false,
  "renderApproved": false,
  "overall": "pending-side-and-render"
}
```

被拒的候选使用 decision=rejected 并记具体坐标／结构及原因；侧图用独立 `side-review.json`，渲染另记结果。审批不跨 hash、不跨重试继承。真实用户项目不能因测试项目里自动执行过 confirm 就省略人工确认。

## 完成与未完成的报告规则

- 四项 pilot 通过：只能报告四项的已完成阶段；其余25项 pending。
- 10类别各至少一款通过：只能报告类别有代表样本，不等于29款困难边界完成。
- 29款所有必需阶段通过：可报告本矩阵完整完成，列出模型配置、真实尝试数、失败数和迭代后通过情况。仍不能宣称自由文本所有设计、所有模型或所有源类型都可靠。
- 正面、侧图、密集陈列、手机、材质和业务链路分别报告；真实试穿及多件生成保真不属于本矩阵的自动结论。
- 本文件和 JSON 定义验收，没有调用供应商 API，也没有把照片素材／本机替身／测试全绿计为模型效果通过。
