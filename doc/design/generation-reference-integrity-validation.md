# 生成参考图完整性验证

日期：2026-11-09。范围为图片生成请求、Amux 图片提交和真实本地工作流结果链路，保留现有森织界面与织芽形象。没有调用付费服务、启动生产 Worker、运行全仓检查或 CI，也没有提交推送。

## 复现与修复

修复前，82项定向测试中新增的7项失败，分别覆盖以下问题：

- 新设计只带 `referenceImages` 或 `referenceImageUrls` 时，适配器仍选择纯文字生成。
- 图片修改使用单独原图和额外参考时，上传列表只有额外参考，遗漏原图。
- 面料等参考用于新设计时，仍附加保持第一张图身份、构图的修改约束。
- 原图加16张额外参考未检查合计数量，原图被遗漏后看起来仍未超限。
- 显式参考列表被画布编译参考覆盖；编译出17张时静默截到16张继续入队。

`packages/ai/src/generation-image-inputs.ts` 统一解析图片列表，并供请求校验、生成入队和适配器使用。新设计的显式列表优先，单图字段作为旧接口别名；修改和局部重绘固定原图在第一张。完整列表已经包含原图时不会重复上传，但同一原图的不同用途仍保留并指向图片1。其他参考的用途和权重分别保留，提示词明确关联实际上传图片编号。

图片上限为合计16张，局部重绘蒙版单独提交；编号意见修改在入队时预留一张标记图。超限在读取图片或入队前明确拒绝，不截断列表。显式空列表也不被隐式画布参考覆盖。更新原图签名时同时更新完整参考列表中的原图别名，避免同一原图重复占位。

参考引导的新设计使用创作说明；保持原图身份和构图仅用于修改已有图片。局部重绘既有的选区约束和第一张原图/独立蒙版协议保留。任一参考读取失败，不提交不完整图片，也不在适配器内降级为纯文字生成。

## 真实链路证据

新增 `apps/api/src/modules/generation/generation-references.integration.spec.ts`，经过真实工作流服务、PostgreSQL、独立 Redis 队列、私有 MinIO、生成处理器、实际 AI 请求校验及 Amux 组装。图片读取使用实际签名下载；只替换供应商传输的响应，不访问供应商。

四个场景：

1. 新设计：两张独立图片按面料和细节用途上传，不能走纯文字接口。
2. 修改：即使画布节点顺序把参考排在原图之前，实际上传仍为原图、面料、细节；提示词编号逐一对应。
3. 编号意见：原图、带编号的实际标记图、面料、细节完整上传；编号说明和位置保持，临时标记图随后清理。
4. 文件缺失：入队后删除一张参考的测试文件，任务明确失败；不调用生成传输、不创建结果资产、不计入成功生成次数。

成功场景逐字节比对上传文件、保存输出和不变的原始素材，检查任务、执行记录、尝试记录、画布结果、母图及根版本关联。重复执行同一请求和再次同步不产生第二份结果，也不重复计数。测试结束清理各自的队列、用户、项目和对象存储文件。

同时检查工作流参考配置：现有 `referenceInputs` 按节点编号指定用途与权重，没有用户指定图片顺序的字段。测试故意使配置数组、连接顺序与节点顺序不同，验证用途按节点匹配，最终提示词按实际上传顺序编号；本轮没有改变工作流顺序契约。

## 后续边界

完整输入和正确结果关联不证明真实模型能准确理解用途、控制参考强度或达到预期画质。16张上限属于现行平台请求契约，本轮没有重新核实供应商最新限额。

本轮结束时，普通生成参考仍涉及临时签名地址，长时间排队、重试和原素材变更后的稳定性需要接续核查。随后完成的文件身份核验、每次尝试更新地址及原图记录变化检查见[排队与重试恢复](generation-reference-recovery-validation.md)，其验证结果单独记录；局部重绘继续沿用独立稳定输入机制。
