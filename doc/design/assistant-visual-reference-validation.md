# 多图分析输入与引用记录验证

日期：2026-11-09，北京时间。接续画布多素材引用与长会话优化，本轮核对显式引用、实际附图、分轮补读和历史引用记录的一致性。

## 已复现的问题

定向用例首次运行共27项，5项失败、22项通过，明确复现：

- 同一文件在画布的多个副本会分别占用图片名额。8个副本即可占满一轮8张图片，后面的独立参考图无法附入。
- 显式引用和讨论焦点包含相同对象时，后出现的焦点位置覆盖了原先的引用顺序。
- 补读后仍沿用初始的分析成功/处理中数量；本轮记录只保留最后一批附图。
- 一轮里请求读取的中间图片可能在真正发送给模型前被后续读取替换，不能把所有读取操作都记成已经传入。

后续审查补充断言，又复现了统计已更新但图片目录仍显示旧的“尚未就绪”。已同步修正下一次模型请求的目录和信息整合区。上述问题均由实际业务函数的测试发现；不是通过复写选择算法来测试测试代码本身。

## 当前行为

- 保留每次最多8张不同来源图片的上限，不因聊天允许引用16个对象就盲目扩大每次请求。文字对象、图片副本和图片数量分别处理。
- 同一可信文件或资产的画布副本共用图片数据，各自保留节点身份、名称、引用角色和图片序号。同名的不同文件不会合并。去重在现有项目和文件权限验证之后进行。
- 显式引用保持首次出现的顺序；重复的讨论焦点不能把它重新排序。达到图片上限后，仍可给已附图片添加其他副本绑定。
- 每次最多64个对象绑定；超过范围仍保留在图片目录与未附图清单中，显式引用优先。图片请求仍最多8张。
- 补读后重新计算当前目录、摘要状态、附图对象和未附图对象；最新读取已不可用的对象不会从上一批复活旧图片。
- 在实际模型请求边界收集累计传入对象和不同来源图片数。一轮内读取后又被替换、从未进入请求的图片不计入。最多5次规划请求的记录有界，名称快照最多320个图片对象。
- 回复保存本轮累计的图片对象名称，最后一次请求的图片绑定单独保留。重新读取对话不会丢掉之前请求的记录；普通引用和讨论对象仍分别保存。
- 引用详情显示“本轮累计传入N张图片，对应M个画布对象”，同图副本只计一次。明确列出仍未传入的显式图片，并提供继续引用的说明。
- 摘要失败与是否附图分开：界面使用“分析不可用”，避免把摘要失败直接说成图片完全没有传入。旧消息没有独立图片计数时，只显示对象数量，不补造去重后的张数。

新增的统计字段均为可选字段，不需数据库迁移；旧消息仍可读取。发布本变更时需要同时包含共享契约、API与Web，但本轮没有部署。

## 实际链路验证

新集成用例使用真实本地PostgreSQL和私有MinIO，创建隔离账号、项目、会话与9个不同的WebP文件。画布有16个引用对象，其中8个为同一文件的副本，其余8个对应独立文件。

第一请求附入8张图片，对应15个画布对象；第二请求补读剩余图片，每次仍为8张以内。测试逐项核对请求中的图片字节与文件身份，最终累计记录9张图片、16个对象，重新读取消息得到相同引用记录。回复记录不包含私有对象路径或base64图片数据。所有测试文件、摘要和账号在结束后清理。

视觉摘要使用经过契约校验的测试记录，分析模型回复使用受控数据；没有投递实际视觉分析队列、调用真实模型或生成任务。此用例证明文件读取、输入绑定和持久化往返，不证明模型理解和生成质量，也不是完整HTTP认证验证。

集成测试最初暴露了夹具的文件字段名及必填字段、回复协议字段和摘要不确定性字段错误。修正夹具后通过，没有因此放宽产品校验。

## 验证边界与后续

累计传入记录描述当前成功处理过程中各次请求的输入，不保证最终一次请求同时包含这些图片，不代表模型具有跨请求的完整视觉记忆；失败尝试的图片轨迹没有新增独立持久化。真实多图理解、跨轮比较质量、生成时的参考遵循程度、语义拆层和图片内文字编辑仍需独立验证。接下来继续核对参考对象到实际生成请求的顺序、用途及结果对应关系。

按用户要求，本次只通过助手远程联网工具尝试访问Lovart，没有使用本机网络访问该站点。工具未返回可核验正文；中途关于成功读取和引用的表述已明确更正，不形成新官方证据。参考边界见[能力对照](lovart-capability-review.md)。全平台对标目标继续进行，不以本轮通过为完成声明。
